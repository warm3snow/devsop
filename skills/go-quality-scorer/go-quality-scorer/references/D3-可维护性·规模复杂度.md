# D3 可维护性·规模复杂度 评分详解

## 概述

D3 维度评估代码的**可维护性**，核心关切是"代码是否容易理解、修改、测试"。

**版本 2.0**（2026-06-26）新增**规模复杂度**子模型，在原有复杂度基础上补充代码规模、可维护性指数等量化指标。

---

## 评分结构

```
D3 最终得分 = (D3_基础 × 60%) + (D3_规模复杂度 × 40%)
│
├─ D3_基础（60%）
│  ├ 圈复杂度（CC）✓ 已有
│  ├ 代码风格 ✓ 已有
│  └ 命名规范 ✓ 已有
│
└─ D3_规模复杂度（40%）新增
   ├ 平均圈复杂度（Avg CC）     20%
   ├ 峰值圈复杂度（Peak CC）    15%
   ├ 认知复杂度（Cognitive CC） 15%
   ├ 代码规模（SLOC）           20%
   ├ 函数长度分布               15%
   └ 可维护性指数（MI）         15%
```

---

## 六个新指标详解

### 1. 平均圈复杂度（Avg CC）

**定义**：函数圈复杂度的平均值。

**工具**：`gocyclo`

**阈值**：
| 评级 | Avg CC | 得分 | 说明 |
|------|--------|------|------|
| A | ≤ 5 | 100 | 极佳，函数逻辑简洁 |
| B | 6-10 | 80 | 良好，可接受 |
| C | 11-15 | 60 | 一般，需关注 |
| D | 16-25 | 40 | 差，需改进 |
| F | > 25 | 0 | 极差，触发红线 |

**优秀例子**（Avg CC = 4）：
```go
func Add(a, b int) int {
    return a + b
}

func Divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("division by zero")
    }
    return a / b, nil
}
```

**差的例子**（Avg CC = 18）：
```go
func Process(status string, flag bool, value int) string {
    if status == "active" {
        if flag {
            if value > 100 {
                if condition1 {
                    // ...深层嵌套
                }
            }
        }
    }
    // ... 复杂条件分支
}
```

---

### 2. 峰值圈复杂度（Peak CC）

**定义**：项目中单个函数的最高圈复杂度。

**工具**：`gocyclo`

**阈值**：
| Peak CC | 得分 | 说明 |
|---------|------|------|
| ≤ 10 | 100 | 极佳，可测性强 |
| 11-20 | 75 | 一般，可以接受 |
| 21-50 | 50 | 差，难以测试 |
| > 50 | 0 | **红线**，不可测 |

**红线触发**：
- Peak CC > 50 → 直接标记为不可测函数
- 需强制重构

---

### 3. 认知复杂度（Cognitive CC）

**定义**：从**人脑感受**角度衡量复杂度，与圈复杂度互补。

特点：
- 忽略简单的嵌套（如 `if` 后面的 `return`）
- 加重嵌套分支权重（嵌套越深，认知负荷越高）
- 与 SonarQube 算法对齐

**工具**：`gocognit`

**阈值**：
| Cognitive CC | 得分 | 说明 |
|-------------|------|------|
| ≤ 10 | 100 | 极佳，易理解 |
| 11-15 | 80 | 良好 |
| 16-25 | 60 | 一般 |
| 26-35 | 40 | 差 |
| > 35 | 20 | 极差，需重构 |

**例子对比**（CC vs Cognitive CC）：
```go
// 圈复杂度 = 5，认知复杂度 = 5（简单条件）
if a > 0 {
    b = 1
}
if c > 0 {
    d = 2
}

// ─────────────────────────────────────

// 圈复杂度 = 4，认知复杂度 = 8（嵌套加权）
if a > 0 {
    if b > 0 {
        if c > 0 {
            d = 1
        }
    }
}
```

---

### 4. 代码规模（SLOC）

**定义**：Source Lines of Code，剔除注释和空行的有效代码行数。

**工具**：`scc`（Sloc Cloc and Code）

**计算范围**：
- ✓ 有效代码行（包括 Go 包声明、import）
- ✗ 注释行
- ✗ 空行
- ✗ 大括号单独占行

**阈值**（单文件）：
| SLOC | 得分 | 说明 |
|------|------|------|
| ≤ 300 | 100 | 模块化好，易理解 |
| 301-800 | 85 | 良好 |
| 801-1500 | 70 | 一般，需关注 |
| 1501-2000 | 50 | 差，需拆分 |
| > 2000 | 0 | **红线**，巨兽文件 |

**整个项目规模参考**：
| 项目规模 | 推荐 SLOC | 典型项目例 |
|---------|----------|----------|
| 小型库 | < 5K | 单个 util 包 |
| 中型服务 | 10-50K | 订单微服务 |
| 大型应用 | 50-200K | 平台级应用 |

---

### 5. 函数长度分布

**定义**：统计函数行数，关注异常长函数比例。

**指标**：
- 平均函数行数（Avg Function Length）
- 超长函数比例（% of functions > 80 lines）

**阈值**：
| 平均函数行数 | 得分 | 超长函数占比 | 加分/扣分 |
|----------|------|----------|---------|
| ≤ 30 | 100 | < 5% | +0 |
| 31-50 | 80 | 5-10% | -5 |
| 51-80 | 60 | 10-20% | -15 |
| 81-150 | 40 | 20-40% | -30 |
| > 150 | 0 | > 40% | -50 |

**优秀例子**（平均 25 行）：
```go
func Validate(email string) bool {
    if email == "" {
        return false
    }
    return strings.Contains(email, "@")
}

func Send(msg string) error {
    return client.Post(msg)
}
```

**差的例子**（平均 120 行）：
```go
func HandleRequest(r *http.Request) {
    // 60 行验证
    // 30 行业务逻辑
    // 20 行错误处理
    // 10 行缓存更新
    // 混杂在一起
}
```

### 6. 可维护性指数（MI）

**定义**：基于 Halstead 体积、圈复杂度、代码行数的综合指数。

**公式**（Visual Studio 派生）：
```
V = (N1+N2)·log₂(n1+n2)  // Halstead 体积
    其中 N1 = 运算符总数
         N2 = 操作数总数
         n1 = 唯一运算符数
         n2 = 唯一操作数数

MI = MAX(0, (171 − 5.2·ln(V) − 0.23·CC − 16.2·ln(LOC)) × 100 / 171)
    其中 CC = 圈复杂度
         LOC = 代码行数
```

**阈值**：
| MI 值 | 评级 | 得分 | 说明 |
|------|------|------|------|
| 85-100 | ⭐⭐⭐ 高 | 100 | 易维护 |
| 65-84 | ⭐⭐ 中 | 85 | 正常 |
| 50-64 | ⭐ 低 | 60 | 有隐患 |
| 25-49 | 极低 | 30 | 难以维护 |
| < 25 | 不可维护 | 0 | **红区** |

**含义**：
- **MI ≥ 65**：代码质量良好，新手也能理解
- **MI 50-64**：代码需要一定经验才能修改，有风险
- **MI < 50**：代码高风险，修改易引入 bug

## 红线规则

### D3 新增红线

1. **单函数 CC > 50**
   - 表现：函数无法通过单元测试全覆盖
   - 处置：强制拆分

2. **平均 CC > 25**
   - 表现：整体代码结构混乱
   - 处置：架构重审

3. **单文件 SLOC > 2000**
   - 表现：巨兽文件，维护成本极高
   - 处置：拆分成多个文件/包

4. **MI < 10 的文件占比 > 10%**
   - 表现：大量不可维护代码
   - 处置：立即重构

## 评分示例

### 案例 1：优秀代码（D3 = 88）

```
D3_基础 = 90
  - CC 平均 = 8 → 85 分
  - 风格 = 95 分
  - 命名 = 90 分
  - 基础加权 = (85+95+90) / 3 ≈ 90 分

D3_规模复杂度 = 85
  - Avg CC = 8 → 85
  - Peak CC = 18 → 75
  - Cognitive CC = 12 → 80
  - SLOC = 500 → 90
  - 函数长度 = 平均 35 行 → 85
  - MI = 72 → 85
  - 加权 = 85 分

最终 D3 = 90×0.6 + 85×0.4 = 54 + 34 = 88
```

### 案例 2：一般代码（D3 = 65）

```
D3_基础 = 70
  - CC 平均 = 15 → 60 分
  - 风格 = 75 分
  - 命名 = 75 分
  - 基础加权 ≈ 70 分

D3_规模复杂度 = 60
  - Avg CC = 15 → 60
  - Peak CC = 28 → 65
  - Cognitive CC = 22 → 65
  - SLOC = 1200 → 70
  - 函数长度 = 平均 60 行 → 65
  - MI = 55 → 60
  - 加权 = 64 分

最终 D3 = 70×0.6 + 60×0.4 = 42 + 24 = 66
```

## 审查检查清单

- [ ] 最复杂的函数 CC < 20
- [ ] 平均 CC < 10
- [ ] 认知复杂度 < 15
- [ ] 所有函数 < 100 行
- [ ] 平均函数 < 50 行
- [ ] 单文件 < 800 行
- [ ] 无单文件 > 2000 行
- [ ] MI 指数 > 65 的文件占比 > 90%
- [ ] 命名清晰，一眼看懂
- [ ] 注释覆盖复杂逻辑

## 改进路线

### 快速改进（1-2 天）
1. 使用 IDE 重构工具拆分超长函数
2. 提取重复的条件逻辑
3. 优化 if-else 嵌套

### 中期改进（1-2 周）
1. 引入 strategy 模式降低 CC
2. 应用 guard clause 简化流程
3. 拆分巨兽文件

### 长期改进（持续）
1. Code Review 时重点关注复杂度
2. 建立 CI/CD 质量门槛（D3 ≥ 75）
3. 定期运行分析工具，追踪趋势

```bash
# 查看圈复杂度

# 规模统计
scc -l go ./...

# 代码行数统计
scc --by-file ./...

# MI 计算（Python 脚本）
python3 calculate-mi.py ./...
```
