# Code Review Standards

> Status: Draft | Maintainer: {{name}} | Last Updated: {{YYYY-MM-DD}}

## Scope

All PRs/MRs merged into `{{main / master}}` must go through review; AI-generated code is subject to the same rule.

## 1. Submitter Constraints

- ❌ Pushing directly to `{{main / master}}` (must go through feature branch + PR)
- ❌ PR > **500** lines not split (split by module/layer)
- ❌ PR not linked to an issue-tracker ticket number
- ❌ Submitting AI code without understanding it (the submitter must be able to answer: "What does this code do? Why is it written this way?")
- ❌ Deleting existing tests (unless there is a clear reason and it is stated in the PR description)
- ❌ Introducing new dependencies without explaining the reason in the commit message
- ❌ Committing `.env` / `*.key` / `*.pem` / `credentials.json` / build artifacts
- ✅ PR description includes: background, changes, impact surface, testing approach, rollback plan

## 2. Submitter Self-Checklist (pre-commit)

- [ ] `make build` passes
- [ ] `make lint` passes
- [ ] `make ut` passes, coverage does not decrease (≥**60%**)
- [ ] New/modified logic has corresponding tests (TDD: red first, then green)
- [ ] No `.env` / `*.key` / `vendor/` / `node_modules/` / `bin/` / `dist/` etc.
- [ ] Commit title follows `<type>(<module-or-service>): <subject>` (`feat` / `fix` / `docs` / `refactor`)
- [ ] I **fully understand** what this code does (not generated by AI and committed without reading)
- [ ] Linked issue-tracker ticket number

## 3. Reviewer Checklist

### P0 (Must check / blocks merge)

#### Business Correctness
- [ ] Changes match the requirements doc/Spec, no scope creep
- [ ] Edge cases: empty values, null, overlong input, concurrency, retry idempotency
- [ ] Error handling complete, no swallowed errors (`_ = err` must have a reason comment)

#### Security
- [ ] No SQL injection (parameterized queries)
- [ ] No command injection (structured API calls)
- [ ] No path traversal (`..` validation)
- [ ] No hardcoded sensitive information (secrets, AK/SK, passwords, internal IPs)
- [ ] Log redaction (ID card numbers, phone numbers, Tokens, passwords not printed)
- [ ] Authentication/authorization checks in place (operation permission, data permission)
- [ ] Input validation complete (whitelist + validator)
- [ ] Encryption algorithms conform to standards (no MD5/SHA1/DES/RC4)

#### Resource Safety
- [ ] Resource release paired (defer / with / try-with-resources)
- [ ] No goroutine/thread/Promise leaks
- [ ] Context correctly propagated and responds to cancellation
- [ ] No memory leaks (subscriptions, listeners, caches)

#### Testing
- [ ] New code has test coverage (including normal + edge + error cases)
- [ ] Assertions are effective (not message-string assertions)
- [ ] Integration tests use a real DB (**forbidden** to mock DB)
- [ ] Modified logic must have corresponding unit test adjustments

### P1 (Recommended / strongly suggested)

- [ ] Consistent naming, comments explain Why
- [ ] Functions ≤80 lines, nesting ≤4 levels, line length ≤120 columns
- [ ] Complexity under control, no obvious bad smells (duplication, overlong parameter lists, god classes)
- [ ] Performance: N+1, unnecessary full table scans, memory waste
- [ ] Observability: key paths have logging, trace identifiers, key metric instrumentation
- [ ] Framework conventions (e.g. go-zero: Logic injects dependencies via svcCtx, context propagation)

### AI Hallucination Specific

> As AI-generated code accounts for an increasing share, the following must be additionally checked:

- [ ] Referenced methods/fields/packages **actually exist** (guard against AI fabricating APIs)
- [ ] Third-party library versions/usages match `go.mod` / `package.json` / `requirements.txt`
- [ ] No imports that "look right but do not actually exist"
- [ ] Business logic matches the actual data flow (not an AI-imagined flow)
- [ ] Key magic values (timeouts, thresholds, rate-limit parameters) have a basis, not arbitrary "reasonable numbers"
- [ ] Error codes reference constants that actually exist

### Optional (per scenario)

- [ ] Internationalization: whether hardcoded text should be extracted
- [ ] API and data-model changes match the requirements and have relevant tests
- [ ] Documentation: whether README / ARCHITECTURE / OpenAPI are kept in sync

## 4. Review Reply Etiquette

- Distinguish severity:
  - `must-fix` (blocking)
  - `should-fix` (strongly suggested)
  - `nice-to-have` (optional improvement)
  - `nit` (trivial, does not block merge)
  - `question` (clarification, submitter must respond)
- Give **concrete modification suggestions** rather than "this is badly written"
- Submitter: every comment must be answered (accept / explain / defer + follow-up issue)
- Cannot merge if comments have no response and no changes

## 5. Merge Requirements

- ≥**1** Reviewer approval (key modules ≥**2**; cross-module changes need the responsible person for each module)
- CI fully green (build / lint / ut / integration-test)
- All `must-fix` items resolved
- No unanswered `question`s
- No `Security Critical` alerts

## 6. AI-Assisted Review

- May use `/code-review` or a similar Skill to get a preliminary review report
- AI report serves as **reference input**, does **not replace** human review
- Human review must be done by someone other than the submitter (one cannot review one's own PR)

## 7. Emergency Merge Process (hotfix)

- Only for: production incidents, security vulnerabilities, forced removals
- Required:
  - At least 1 Reviewer reviews synchronously (voice/phone)
  - Complete PR description and regression tests within 24 hours
  - Post-incident retrospective recorded in [failures.md](failures.md)
